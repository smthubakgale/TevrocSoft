Tevroc SDK: Build scalable Tevroc apps with JavaScript

A structured developer guide for installing Tevroc SDK, creating the client, and using auth, entities, integrations, and offline support across browser and native apps.

UpdatedAugust 8, 2026 Read time8 min AudienceDevelopers

Welcome to the Tevroc SDK learning path. In this chapter, you will discover how a single JavaScript client can power authentication, data access, payments, files, integrations, and offline-first behavior across web and native apps. Think of this guide as a hands-on roadmap that builds your Tevroc app story step by step.

By the end of this guide, you will understand the core SDK concepts and have practical examples you can copy into your own project. The focus is on real developer workflows: installing the SDK, wiring a client, authenticating users, working with entities, and extending functionality with integrations and offline sync.

Why this matters

Instead of stitching together many separate APIs, you can use one consistent SDK object to handle the entire app experience. That makes your code easier to maintain, easier to test, and easier to scale as your product grows.

Developer note

Think of Tevroc SDK as a reliable bridge between your frontend and the services behind it. The more you reuse the same client object, the less duplicated logic you need in your UI.

Getting started

The first chapter is about setting up your environment. Install the SDK, choose a runtime, and prepare the link between your app and the Tevroc worker. This is the foundation for every real-world feature you will build.

Choose the installation path that matches your project: modern web apps should prefer npm/ESM, while quick prototypes or static pages can use the browser script bundle. Either approach delivers the same runtime API surface.

Install the SDK

npm / ESM

npm install tevrocsdk

Use this in your React, Vue, Svelte, or native hybrid app to import the SDK as a standard module.

Browser

<script src="https://unpkg.com/tevrocsdk@latest/tevroc-sdk.min.js"></script>

Add this script tag directly to a static page or webview for fast testing without a build step.

Starter checklist

A strong first pass usually means three things: install the SDK, connect it to your worker URL, and create a client once so the rest of your app can reuse that same configuration.

Your first Tevroc bootstrap

import { createClient } from "tevrocsdk";

const tevroc = createClient({
  baseUrl: "https://your-worker.example.workers.dev",
  serviceUrl: "https://services.example.com",
  appId: "tevroc-portal",
  appName: "Tevroc Portal",
  debug: true,
});

await tevroc.auth.me();

This simple bootstrap gives you a reliable starting point for auth, entity access, and future integrations. Once it works, you can layer on login pages, dashboards, file uploads, and native experiences without changing your core setup.

Enable `debug: true` during development to trace request execution, offline sync events, and native helper diagnostics across browser and native shells.

Installation and setup

In this section you will make the SDK available to your app. Whether you choose npm for a modern JavaScript project or a browser bundle for quick prototypes, the install step unlocks the same Tevroc APIs across platforms.

If you are working on the Tevroc SDK repository itself, the local install path lets your application consume the SDK source directly while you iterate. For production apps, install the published npm package or deploy the compiled bundle from your build process.

Example: local package install

npm install ../tevrocsdk
cd ../tevrocsdk && npm run build

Use this flow when your app and SDK source are in the same workspace. After building, point your app import to the generated SDK files or publish the package to your private registry.

Native and desktop integration

Tevroc SDK works naturally in web apps, but it also fits mobile and desktop shells. When you need OAuth callbacks, native file access, or deep links, the host app usually provides the platform bridge while the SDK supplies the API client, auth helpers, storage wrappers, and integrations that stay consistent across environments.

A good native integration strategy is usually simple: keep the core application logic in the web layer, then add the minimum platform-specific plumbing required for redirects, file handling, and OS-level events. That keeps your app portable while still feeling native where it matters most.

Capacitor (mobile)

  • Declare the app identity and a custom URL scheme in your Capacitor config so the app can receive OAuth redirects.
  • Add the Capacitor app and browser plugins so the SDK can use native file save, toast, and browser flows when available.
  • Add an Android intent filter so the platform can route callback URLs back into your app.
  • Listen for the platform event and forward the URL into your auth callback flow.
  • For offline support, Tevroc keeps using native storage when the Capacitor SQLite plugin is available and falls back to localStorage in unsupported environments.

import { App } from "@capacitor/app";

Tauri (desktop)

  • Register a custom protocol in your Tauri config so the desktop app can receive deep links.
  • Add the relevant Rust plugins for deep-link handling and single-instance behavior.
  • Emit a frontend event from the Rust side and listen for it in your app.

Typical file locations

project-root/
├── src-tauri/
│   ├── tauri.conf.json
│   ├── Cargo.toml
│   └── src/
│       └── lib.rs
└── src/
    └── frontend code that listens for deep-link events

src-tauri/tauri.conf.json

{
  "identifier": "com.example.desktop",
  "plugins": {
    "deep-link": {
      "desktop": {
        "schemes": ["myapp"]
      }
    }
  }
}

src-tauri/Cargo.toml

[dependencies]
tauri = { version = "2", features = [] }
tauri-plugin-deep-link = "2"
tauri-plugin-single-instance = "2"

src-tauri/src/lib.rs

use tauri::{Manager, Emitter};
use tauri_plugin_deep_link::DeepLinkExt;
use serde_json::json;

#[cfg_attr(mobile, tauri::mobile_entry_point)]
pub fn run() {
    let builder = tauri::Builder::default()
        .plugin(tauri_plugin_single_instance::init(|app, argv, _cwd| {
            if let Some(url) = argv.get(1) {
                let _ = app.emit_to("main", "deep-link://open-url", json!(url));
            }
        }))
        .plugin(tauri_plugin_deep_link::init())
        .setup(|app| {
            #[cfg(any(target_os = "linux", all(debug_assertions, windows)))]
            app.deep_link().register_all()?;
            Ok(())
        });

    builder.run(tauri::generate_context!()).expect("error while running app");
}

src/main.ts

import { listen } from "@tauri-apps/api/event";

listen("deep-link://open-url", (event) => {
  handleAuthCallback(event.payload as string);
});

Choosing the right shell

Choose Capacitor when your main goal is to ship a polished mobile app with web-first logic and native bridge features. Choose Tauri when you want a desktop-first experience with deeper OS integration and a Rust-powered backend layer. In many teams, the web app stays the same and only the host shell changes.

  • Capacitor is best for mobile-first teams that want familiar web development with native app wrappers.
  • Tauri is best for desktop teams that need tighter window, file, and OS integration.
  • Both work well when you keep the Tevroc client central and let the shell only handle platform-specific events.

Practical rollout checklist

  • Start with web auth and worker URLs before you add native callbacks.
  • Make sure your custom URL scheme or deep-link protocol is registered first.
  • Test the full login callback flow on the target device or desktop shell before shipping.
  • Use the native file and storage helpers only when the platform really needs them.
  • Keep the Tevroc client initialization identical across web, mobile, and desktop so your app behaves consistently.

What this gives you in practice

Once the shell is wired correctly, your app can open auth flows, receive callbacks, save files, and keep state in a way that feels native without forcing you to rewrite the entire application. That is the real value of Tevroc’s platform-aware integration model.

Setup notes for local apps and desktop shells

If you are consuming the SDK from a monorepo or local workspace, point your app dependency at the local package folder and rebuild the SDK output before launching the app.

npm install ../tevrocsdk
cd ../tevrocsdk && npm run build

For Tauri desktop apps, ensure the frontend can access the Tauri bridge and the Rust side exposes the PDF command. The recommended setup is to add the Tauri plugins for deep-link, dialog, fs, opener, and shell, expose a command such as open_pdf_file from the Rust integration layer, and keep the base64 dependency in your Tauri manifest.

Added services and capabilities

  • PDF helpers: tevroc.pdf.downloadPdf, tevroc.pdf.previewPdf, and tevroc.pdf.printPdf
  • Desktop-friendly PDF handling for Tauri, where the SDK writes a temporary PDF and opens it with the host OS viewer
  • Offline sync support with a safe fallback when Capacitor background-task support is unavailable
  • Native store helpers for web/localStorage fallback and native persistence in Capacitor and Tauri contexts
  • Auth, entity, integration, payments, and file helpers that work through the same unified client object

Create a client

This is the moment your app becomes Tevroc-aware. The client wires your runtime to Tevroc services and shares app identity, base URLs, and environment details. Treat it as the central control plane for everything you build next.

The client configuration tells Tevroc where your APIs are hosted and how to label requests in logs and dashboards. That means authentication, entity access, file URLs, and integrations all use the same shared runtime context.

import { createClient } from "tevrocsdk";

const tevroc = createClient({
  baseUrl: "https://your-worker.example.workers.dev",
  serviceUrl: "https://services.example.com",
  appId: "tevroc-portal",
  appName: "Tevroc Portal",
});

You can also reuse an existing access token to keep users signed in across refreshes:

const tevroc = createClient({
  baseUrl: "https://your-worker.example.workers.dev",
  token: localStorage.getItem("tevroc_access_token"),
  appId: "tevroc-portal",
  appName: "Tevroc Portal",
});

Environment-aware setup example

const isProd = window.location.hostname.includes("tevrocsoft.co.za");

const tevroc = createClient({
  baseUrl: isProd ? "https://prod-worker.example.workers.dev" : "https://dev-worker.example.workers.dev",
  appId: "tevroc-portal",
  appName: "Tevroc Portal",
});

Using environment-based values keeps local development separate from production, which is especially helpful when you are testing new features or staging migrations.

Authentication

Users expect secure sign-in and seamless identity handling. In this chapter, you will learn how Tevroc manages login, registration, password resets, and social sign-in while keeping your UX fast and reliable.

A good auth flow balances security and speed: prompt users only when necessary, preserve session state, and handle errors without blocking the experience. Tevroc helps you build that by exposing simple auth methods and session helpers.

Authentication flow

Loading auth flow diagram...

Sign in and profile

const { token, user } = await tevroc.auth.login({
  email: "ada@example.com",
  password: "correct horse battery staple",
});

const me = await tevroc.auth.me();

The login call returns both the current user and a fresh token. Use tevroc.auth.me() to validate the session and fetch profile details after page refresh.

Register, logout and reset

await tevroc.auth.register({
  email: "ada@example.com",
  password: "correct horse battery staple",
});

await tevroc.auth.logout();
await tevroc.auth.verifyOtp({ code: "123456" });
await tevroc.auth.changePassword({ oldPassword: "old", newPassword: "new" });
await tevroc.auth.resetPassword({ email: "ada@example.com" });
await tevroc.auth.loginUrl("/dashboard");

Use registration to create new users, logout to clear the current session, verify OTP codes, change a password, and reset a forgotten password as part of a recovery flow.

Google sign-in

await tevroc.auth.googleLogin({
  appId: "tevroc-portal",
  appName: "Tevroc Portal",
  serviceUrl: "https://services.example.com",
});

tevroc.auth.onGoogleLogin((user, error) => {
  if (error) {
    console.error("Google login failed", error);
    return;
  }

  console.log("Google user", user);
});

await tevroc.auth.loginWithGoogle({
  accessToken: googleAccessToken,
});

await tevroc.auth.loginWithProvider("google", "/dashboard");

Google login is a fast way to let users authenticate without managing passwords. Tevroc supports provider-based social auth alongside traditional email/password flows.

Work with entities

Entities are the backbone of your app’s data model. Learn how to create, query, update, and delete records, and how entity services help you build dashboards, lists, and workflows with consistent APIs.

With Tevroc entities, your data access patterns remain intuitive and repeatable. Each entity service exposes a predictable set of CRUD and query methods so you can build features without learning dozens of custom endpoints.

Entity architecture

Loading entities diagram...
const created = await tevroc.entities.Project.create({
  name: "Launch site",
  status: "active",
});

const projects = await tevroc.entities.Project.list({ limit: 20 });

const filtered = await tevroc.entities.Project.query({
  filter: { status: "active" },
  limit: 10,
});

await tevroc.entities.Project.update(created.data.id, { status: "done" });

// Use entity results for tables, dashboards, or summary cards.

Query and sort example

const recentProjects = await tevroc.entities.Project.filter(
  { status: "active" },
  { sortBy: "createdAt", direction: "desc" },
  10
);

Filtering and sorting let your UI render the most relevant records first, whether you are building a dashboard, a task board, or a customer view.

Entity lifecycle

Loading entity lifecycle diagram...

Entities move through create, read, update, and sync stages, making it easier to build consistent CRUD interfaces.

The response objects are designed to include both record data and metadata, making pagination and filtering easier to implement in UI components.

Common entity methods

  • list() — fetch a page of records.
  • get(id) — retrieve a single record by its ID.
  • create(record) — save new data.
  • update(id, patch) — patch existing records.
  • delete(id) — remove a record.
  • query({ filter }) — run filtered searches.

Bulk and sync helpers

  • bulkCreate(records) — create many records in one request.
  • bulkUpdate(records) — update multiple records together.
  • bulkDelete(ids) — remove many records at once.
  • import(records) — ingest external data into the entity store.

Call custom functions

Think of custom functions as event-driven actions that run on Tevroc servers. In this section, you’ll see how to trigger logic like notification delivery, data transforms, or automation without hardwiring REST endpoints.

Custom functions are ideal for isolated business logic that doesn’t belong in the client. Use them to keep sensitive code on the server, to integrate with external systems, and to orchestrate multi-step workflows.

Invoke a function

await tevroc.functions.invoke("ping", { hello: "world" });

// Shorthand helper
await tevroc.functions.ping({ hello: "world" });

The first call uses a generic `invoke` method; the second is a convenience shorthand for the same operation. Both let you pass payload data to the server-side function.

Accept payments

Monetization is often the next step after core app features. This section teaches you to add checkout creation, status listeners, and payment lifecycle handling while preserving a clear user flow.

Payment processing should be transparent to users: they need confirmation of success, a clear failure path, and a clean retry experience. Tevroc handles the checkout orchestration while your app focuses on the customer flow.

Create a checkout

await tevroc.payments.create({
  amountZAR: 50,
  appId: "tevroc-portal",
  mode: "web",
});

const unsubscribe = tevroc.payments.onstatus((status, error) => {
  if (error) {
    console.error("Payment listener error", error);
    return;
  }
  console.log("Payment status:", status);
});

Use onstatus to observe checkout progress and trigger UI updates. This keeps your payment flow responsive while the backend handles authorization, confirmation, and receipts.

Work with files and app data

Files and app state are essential for real apps. Here you’ll learn how to store and retrieve documents, images, and settings in a way that works across browser, mobile, and desktop shells.

Tevroc provides helpers for public URLs, private downloads, and native storage so that your file experience remains consistent across platforms. Use the same SDK calls in your web UI and in a mobile native container.

File helpers

const fileUrl = tevroc.files.url("reports/summary.pdf");
const privateFileUrl = tevroc.files.privateUrl("reports/private.pdf");

await tevroc.files.get("reports/summary.pdf");
await tevroc.files.getPrivate("reports/private.pdf");

Use url() for public assets and privateUrl() for signed access. The SDK also supports secure fetches of protected content through getPrivate().

Native store helpers

const store = tevroc.native.store;
const ref = store.ref("settings");
await store.set(ref, { theme: "dark" });
await store.update(ref, { lastOpened: Date.now() });
await store.get(ref);
await store.remove(ref);

The native store lets you persist app state, preferences, and offline caches on the device. This works nicely with offline sync for a seamless native experience.

Google Drive and project helpers

await tevroc.native.files.saveJsonToDrive("project", { ok: true }, null, "user-1");
await tevroc.native.files.readJsonFromDrive("file_123", "user-1");
await tevroc.native.files.deleteFromDrive("file_123", "user-1");

await tevroc.native.projects.upsertUser({
  uid: "u1",
  email: "ada@example.com",
  displayName: "Ada",
  photoURL: "",
});

await tevroc.native.projects.saveProjectMeta("u1", "p1", { title: "Launch" });

These helpers make it easier to bridge app-specific metadata and file storage into the native project and drive layers without building separate adapters.

Offline and sync support

A great app stays useful when the network drops. In this section, you will see how Tevroc keeps data synchronized, caches updates locally, and recovers cleanly when connectivity returns.

Offline support is critical for mobile and field-first applications. Tevroc’s sync layer helps you queue changes locally, detect conflicts, and replay updates as soon as the device regains connectivity.

Sync example

const client = createClient({ baseUrl: 'https://api.example', appId: 'myapp', debug: true });
client.offline.startAutoSync();

client.offline.on('conflict', ({ conflictId }) => {
  console.warn('Conflict detected:', conflictId);
});

Start auto-sync early so cached writes and read operations stay aligned with the latest remote state. When debug mode is enabled, sync events and queue diagnostics are logged to help troubleshoot offline behavior.

What the offline layer does

  • Stores entities and pending file uploads locally using platform-native SQLite when available, with localStorage fallback.
  • Queues create, update, delete, and upload operations while offline and applies them locally immediately so the UI remains responsive.
  • Flushes queued writes and pending uploads periodically or on event-driven resume when connectivity returns.
  • Exposes conflicts via client.offline.listConflicts() and client.offline.resolveConflict(conflictId, resolution).

The SDK attempts to use Capacitor and background-task integrations when available; if those plugins are missing it falls back to foreground sync on resume or focus.

Agents, connectors, logs, and SSO

Tevroc also gives you a higher-level layer for assistants, connector management, logs, and SSO flows. These helpers are especially useful for support experiences, automation dashboards, and admin tooling.

Practical tip

Use agent and connector helpers when you want to introduce guided support, automation, or admin workflows without building a lot of custom infrastructure.

Create agent conversations

const conversation = await tevroc.agents.Support.createConversation({
  title: "Onboarding",
});

await tevroc.agents.Support.addMessage(conversation.data.id, {
  role: "user",
  content: "Help me configure my workspace",
});

const messages = await tevroc.agents.Support.listMessages(conversation.data.id);

Use agent conversations when you want a multi-turn support or assistant experience that feels like a guided workflow rather than a one-off API call.

Connectors, logs, custom integrations, and SSO

await tevroc.connectors.get("slack");

These helpers let your application surface connector status, track operational logs, invoke custom integrations, and complete SSO handoffs with consistent SDK calls.

Make raw requests

const health = await tevroc.request("/health", { auth: false });

Use request() when you need to call a worker route that does not yet have a dedicated helper, while still benefiting from the same authenticated client.

Handle errors

Reliability is built by handling failure cases gracefully. This section shows how Tevroc surfaces structured errors so your app can recover from auth, network, and data issues cleanly.

Instead of letting exceptions break the UI, trap them and decide whether to retry, prompt for login, or show contextual help. Tevroc errors include status codes and structured payloads that make this straightforward.

Reliability tip

Good apps recover gracefully from failures. Treat auth errors, network outages, and validation issues as expected edges of the experience and handle them with clear fallbacks.

Error handling example

import { TevrocError } from "tevrocsdk";

try {
  await tevroc.auth.me();
} catch (error) {
  if (error instanceof TevrocError && error.status === 401) {
    // Ask the user to sign in again.
  } else {
    console.error("Unexpected Tevroc error", error);
  }
}

Use `TevrocError` to distinguish SDK-specific failures from other runtime exceptions. This keeps your error handling targeted and your UX consistent.
